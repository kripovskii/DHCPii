# DHCP: RFC 2131 и RFC 2132

## Что такое DHCP

**DHCP — Dynamic Host Configuration Protocol**, протокол автоматической выдачи сетевых параметров клиенту. Основные документы:

- **RFC 2131** — поведение DHCP-клиента, сервера и relay agent, состояния и обмен сообщениями.
- **RFC 2132** — стандартные DHCP options, то есть содержимое поля `options`.

DHCPv4 работает поверх UDP:

- сервер: `67/udp`;
- клиент: `68/udp`.

Протокол основан на BOOTP, поэтому структура пакета частично наследует BOOTP.

## Зачем нужен DHCP

Клиент может получить:

- IPv4-адрес;
- маску подсети;
- шлюз по умолчанию;
- DNS-серверы;
- DNS-домен;
- время аренды адреса;
- размер MTU;
- NTP-серверы;
- маршруты;
- PXE/boot-параметры;
- пользовательские и vendor-specific параметры.

Главная идея — адрес выдаётся не навсегда, а на **lease time**, то есть срок аренды.

## Структура DHCP-пакета

DHCP-сообщение обычно содержит BOOTP-заголовок:

```
op
htype
hlen
hops
xid
secs
flags
ciaddr
yiaddr
siaddr
giaddr
chaddr
sname
file
options

```

Важные поля:

| Поле | Назначение |
| --- | --- |
| `op` | запрос клиента или ответ сервера |
| `htype` | тип канального адреса, например Ethernet |
| `hlen` | длина hardware address |
| `xid` | transaction ID, связывает запрос с ответом |
| `flags` | например broadcast-флаг |
| `ciaddr` | текущий IP клиента |
| `yiaddr` | адрес, предлагаемый клиенту |
| `siaddr` | адрес следующего сервера, исторически для загрузки |
| `giaddr` | адрес DHCP relay |
| `chaddr` | hardware address клиента |
| `options` | DHCP-специфичная часть |

В `options` обязательно присутствует **Magic Cookie**:

```
63 82 53 63

```

После него идут option TLV:

```
+--------+--------+------------------+
| Code   | Length | Value            |
+--------+--------+------------------+

```

Специальные коды:

- `0` — padding;
- `255` — конец списка options.

Пример:

```
53 01 01

```

Это option 53, длина 1, значение 1 — `DHCPDISCOVER`.

## Основной обмен: DORA

Название DORA происходит от:

1. **Discover**

2. **Offer**

3. **Request**

4. **Ack**

### 1. DHCPDISCOVER

Клиент ещё не знает DHCP-сервер и часто не имеет IP-адреса.

```
0.0.0.0:68 -> 255.255.255.255:67

```

Клиент отправляет `DHCPDISCOVER`, обычно с:

- случайным `xid`;
- `ciaddr = 0.0.0.0`;
- broadcast-флагом;
- option 53 = Discover;
- option 55 = Parameter Request List;
- иногда option 61 = Client Identifier;
- иногда option 50 = Requested IP Address, если клиент пытается восстановить аренду.

### 2. DHCPOFFER

Сервер предлагает адрес:

```
DHCP server -> client

```

В ответе обычно находятся:

- `yiaddr` — предложенный IPv4;
- option 1 — subnet mask;
- option 3 — router;
- option 6 — DNS servers;
- option 51 — IP address lease time;
- option 54 — server identifier;
- option 53 = Offer.

Несколько DHCP-серверов могут прислать несколько Offer. Клиент выбирает один.

### 3. DHCPREQUEST

Клиент явно сообщает, какой Offer принимает.

Ключевые options:

- option 50 — `Requested IP Address`;
- option 54 — `Server Identifier`;
- option 53 = Request.

На начальном этапе клиент обычно отправляет запрос broadcast-ом. Все серверы видят его и понимают:

- выбранный сервер продолжает выдачу;
- остальные серверы должны отказаться от своих предложений.

### 4. DHCPACK

Выбранный сервер подтверждает аренду через `DHCPACK`.

В нём находятся:

- выданный адрес;
- срок аренды;
- остальные конфигурационные параметры.

После ACK клиент может настроить интерфейс и использовать адрес.

Если сервер не может выдать адрес, он отвечает `DHCPNAK`.

## Другие DHCP-сообщения

### DHCPDECLINE

Клиент обнаружил, что предложенный адрес уже используется, например после ARP probe.

```
Client -> Server: DHCPDECLINE

```

Сервер должен пометить адрес как подозрительный или неисправный.

### DHCPRELEASE

Клиент освобождает аренду:

```
Client -> Server: DHCPRELEASE

```

После этого сервер может вернуть адрес в пул.

### DHCPINFORM

Клиент уже имеет IP-адрес, но хочет получить дополнительные параметры DHCP, например DNS или домен.

При `DHCPINFORM` адрес обычно не выдаётся.

### DHCPNAK

Сервер сообщает, что текущая конфигурация недействительна. Возможные причины:

- клиент переместился в другую подсеть;
- адрес больше не принадлежит этой сети;
- сервер не может подтвердить аренду.

Клиент должен прекратить использование адреса и начать процедуру получения заново.

## Аренда и продление

DHCP — это не просто «выдать IP». Клиент должен периодически продлевать аренду.

Пусть:

- `T` — полный срок аренды;
- `T1` — момент начала попытки продления;
- `T2` — момент перехода к широковещательному продлению.

По умолчанию:

```
T1 = 0.5 × T
T2 = 0.875 × T

```

### Состояние INIT-REBOOT

После перезапуска клиент может помнить старый адрес. Он отправляет `DHCPREQUEST`, указывая прежний IP, но ещё не используя его полноценно.

Сервер отвечает:

- `DHCPACK` — адрес можно использовать;
- `DHCPNAK` — адрес нельзя использовать.

### Состояние RENEWING

После `T1` клиент пытается обратиться к серверу напрямую, обычно unicast-ом:

```
Client -> known DHCP server: DHCPREQUEST

```

### Состояние REBINDING

После `T2`, если сервер не отвечает, клиент делает broadcast-запрос. Любой подходящий DHCP-сервер может подтвердить аренду.

### Истечение аренды

Если срок аренды истёк и ACK не получен, клиент обязан прекратить использование IPv4-адреса.

Это важный момент для реализации: нельзя бесконечно продолжать использовать старый адрес только потому, что «сеть пока работает».

## RFC 2132: DHCP Options

RFC 2132 описывает стандартные option codes и их смысл.

### Наиболее важные options

| Код | Название | Смысл |
| --- | --- | --- |
| 1 | Subnet Mask | маска подсети |
| 2 | Time Offset | смещение времени |
| 3 | Router | шлюз по умолчанию |
| 6 | Domain Name Server | DNS-серверы |
| 12 | Host Name | имя клиента |
| 15 | Domain Name | DNS-домен |
| 26 | Interface MTU | MTU интерфейса |
| 28 | Broadcast Address | broadcast-адрес подсети |
| 42 | Network Time Protocol Servers | NTP-серверы |
| 50 | Requested IP Address | запрашиваемый адрес |
| 51 | IP Address Lease Time | срок аренды |
| 53 | DHCP Message Type | тип DHCP-сообщения |
| 54 | Server Identifier | идентификатор сервера |
| 55 | Parameter Request List | список желаемых параметров |
| 57 | Maximum DHCP Message Size | максимальный размер DHCP-пакета |
| 58 | Renewal Time Value | значение T1 |
| 59 | Rebinding Time Value | значение T2 |
| 60 | Vendor Class Identifier | тип клиента |
| 61 | Client Identifier | идентификатор клиента |
| 66 | TFTP Server Name | сервер TFTP |
| 67 | Bootfile Name | имя загрузочного файла |
| 82 | Relay Agent Information | информация от relay |
| 119 | Domain Search | список DNS-search domains |
| 121 | Classless Static Route | бесклассовые статические маршруты |

Некоторые options были определены позднее других RFC, поэтому в реальных реализациях встречаются расширения за пределами первоначального RFC 2132.

### Options 53: DHCP Message Type

Это одна из самых важных options:

| Значение | Тип |
| --- | --- |
| 1 | DHCPDISCOVER |
| 2 | DHCPOFFER |
| 3 | DHCPREQUEST |
| 4 | DHCPDECLINE |
| 5 | DHCPACK |
| 6 | DHCPNAK |
| 7 | DHCPRELEASE |
| 8 | DHCPINFORM |

Тип сообщения находится не в BOOTP-поле, а именно в DHCP options.

### Options 55: Parameter Request List

Клиент сообщает серверу, какие параметры он хочет получить:

```
01 03 06 0f 1a 1c 2a 33 3a

```

Например:

- subnet mask;
- router;
- DNS;
- domain name;
- broadcast address;
- lease time.

Сервер может вернуть не все запрошенные параметры. Поэтому клиент не должен считать, что каждый элемент списка обязательно присутствует в ответе.

### Options 61: Client Identifier

Клиент может идентифицировать себя не только MAC-адресом.

Примеры идентификаторов:

```
01 aa:bb:cc:dd:ee:ff

```

где `01` означает Ethernet, либо произвольная строковая идентичность.

Практическое следствие:

DHCP-сервер должен последовательно использовать client identifier, если клиент его присылает.

Нельзя бездумно считать, что ключ аренды всегда равен MAC-адресу. Иначе могут возникать:

- потеря старой аренды;
- выдача нескольких адресов одному устройству;
- конфликт поведения после смены интерфейса.

### Options 54: Server Identifier

Сервер указывает свой идентификатор, обычно IPv4-адрес интерфейса сервера.

Клиент использует его в `DHCPREQUEST`, чтобы показать, какой Offer он выбрал.

В сетях с несколькими интерфейсами или relay нужно особенно внимательно выбирать значение server identifier. Ошибочный адрес может привести к тому, что клиент будет отправлять renewal не туда.

### Options 82: Relay Agent Information

DHCP-сервер и клиент могут находиться в разных L2-сетях. Тогда DHCP relay пересылает запрос между подсетями.

Relay заполняет поле `giaddr`, а также может добавлять option 82:

- circuit ID;
- remote ID;
- информацию о порте или VLAN.

Сервер может использовать эти данные, чтобы:

- выбрать пул адресов;
- применить политику;
- определить, из какого порта пришёл запрос;
- ограничить выдачу адресов.

Важно: option 82 обычно добавляет и удаляет relay agent. Клиент не должен произвольно доверять её содержимому, если пакет пришёл не от доверенного сетевого устройства.

## Broadcast, unicast и relay

DHCP сложен главным образом из-за того, что в начале клиент может не иметь IP-адреса.

Типичные ситуации:

### Клиент ещё без адреса

```
0.0.0.0:68 -> 255.255.255.255:67

```

### Сервер находится в другой подсети

Маршрутизаторы обычно не пересылают обычный IP broadcast. Для этого используется DHCP relay:

```
Client --broadcast--> Relay --unicast--> Server

```

Relay:

1. получает broadcast от клиента;

2. заполняет `giaddr`;

3. пересылает пакет серверу;

4. получает ответ;

5. доставляет ответ клиенту.

Сервер выбирает адресный пул по `giaddr`.

## Важные детали реализации

### 1. Не полагаться только на MAC

Идентичность клиента может определяться:

1. `client identifier`, если он есть;

2. иначе `chaddr` и аппаратными параметрами.

Серверу нужна стабильная функция выбора ключа аренды.

### 2. Корректно обрабатывать неизвестные options

Клиент должен:

- пропускать неизвестные коды;
- проверять длину;
- не падать из-за vendor-specific extensions;
- сохранять возможность обработать повторяющиеся или нестандартные options согласно своей политике.

DHCP — расширяемый протокол.

### 3. Проверять длины и границы пакета

Нельзя читать option как:

```
value = packet[offset + 2];

```

без проверки:

- существует ли code;
- существует ли length;
- помещается ли value в пакет;
- соответствует ли length ожидаемому формату.

DHCP работает с данными из сети, поэтому parser должен быть строгим.

### 4. Учитывать повторяющиеся options

В корректном пакете многие options должны встречаться один раз, но реальные сети могут быть неидеальны.

Нужно заранее определить политику:

- первое значение;
- последнее значение;
- объединение;
- ошибка для критичных options.

### 5. Проверять конфликт адресов

Некоторые клиенты после получения адреса используют ARP probe. Если адрес занят, клиент отправляет `DHCPDECLINE`.

Серверу не стоит считать любой полученный адрес автоматически свободным без учёта:

- активных leases;
- резервирования;
- статических назначений;
- конфликтов;
- ARP-проверок.

### 6. Учитывать максимальный размер сообщения

Options 57 позволяет клиенту сообщить максимальный размер DHCP-сообщения.

Если параметров много, серверу может потребоваться:

- ограничить ответ;
- не возвращать необязательные options;
- использовать DHCP message overload через поля `file` и `sname`.

### 7. Опции могут быть в разных местах

Стандартно options находятся после BOOTP-заголовка. При message overload дополнительные options могут находиться в:

- `file`;
- `sname`.

Parser должен учитывать option 52 — `DHCP Options Overload`.

### 8. Не доверять только UDP-порту

Порт 67/68 — важный признак, но безопасность DHCP обычно обеспечивается сетевой инфраструктурой:

- DHCP snooping;
- trusted/untrusted ports;
- rate limiting;
- фильтрация rogue DHCP servers;
- проверка option 82.

DHCP сам по себе не предоставляет полноценной криптографической аутентификации в типичном сценарии.

## Пример упрощённого DHCPREQUEST

```
DHCPREQUEST:
  xid: 0x12345678
  ciaddr: 0.0.0.0
  flags: broadcast

  option 53: DHCPREQUEST
  option 50: 192.168.1.42
  option 54: 192.168.1.1
  option 55: 1, 3, 6, 15, 51

```

Смысл:

Клиент с transaction ID `0x12345678` хочет адрес `192.168.1.42`, выбирает DHCP-сервер `192.168.1.1` и просит маску, шлюз, DNS, домен и lease time.

Ответ:

```
DHCPACK:
  yiaddr: 192.168.1.42

  option 1: 255.255.255.0
  option 3: 192.168.1.1
  option 6: 192.168.1.1, 8.8.8.8
  option 15: example.local
  option 51: 86400
  option 58: 43200
  option 59: 75600

```

## Типичный алгоритм DHCP-клиента

Упрощённо:

```
INIT
  |
  v
SELECTING -- DHCPDISCOVER -->
  |
  +-- DHCPOFFER
  |
  v
REQUESTING -- DHCPREQUEST -->
  |
  +-- DHCPACK --> BOUND
  |
  +-- DHCPNAK --> INIT

BOUND
  |
  +-- T1 --> RENEWING
  |             |
  |             +-- DHCPACK --> BOUND
  |
  +-- T2 --> REBINDING
                |
                +-- DHCPACK --> BOUND
                |
                +-- lease expired --> INIT

```

Для разработчика особенно важны:

- `xid` для сопоставления запросов и ответов;
- таймеры и retransmission;
- случайная задержка перед повторной отправкой;
- обработка нескольких Offer;
- переходы после NAK;
- прекращение использования адреса после истечения аренды.

## Что именно задаёт RFC 2131 и что RFC 2132

### RFC 2131

Описывает:

- состояния DHCP-клиента;
- формат взаимодействия клиента и сервера;
- DORA;
- renew/rebind;
- relay agents;
- broadcast/unicast-поведение;
- правила обработки ACK и NAK;
- transaction ID и lease lifecycle.

Это в первую очередь **машина состояний и поведение участников**.

### RFC 2132

Описывает:

- option codes;
- форматы значений;
- обязательность и назначение options;
- стандартные параметры конфигурации;
- BOOTP vendor extensions, используемые DHCP.

Это в первую очередь **словарь параметров внутри сообщений**.

## Короткое резюме

DHCPv4 — это протокол выдачи IPv4-конфигурации по аренде. RFC 2131 описывает, **как участники обмениваются сообщениями и переходят между состояниями**, а RFC 2132 — **какие параметры можно передавать внутри этих сообщений**.

При реализации DHCP нужно думать не только о четырёх пакетах DORA, но и о:

- lease timers;
- relay и `giaddr`;
- client identifier;
- корректном TLV-парсинге;
- broadcast/unicast;
- нескольких серверах;
- DHCPNAK и истечении аренды;
- option 82;
- безопасности против rogue DHCP.
